# Skylark
Skylark - 雲雀(競馬予測素体作成)

netkeiba.com のレース結果を取得して PostgreSQL へ保存し、馬ごとの特徴量を計算します。
さらに、当日開催の中央競馬について「勝率が高いと見積もれるのに、人気がなく、オッズが高い馬」を抽出します。
Bun と TypeScript で動作し、DB アクセスには Drizzle ORM を使います。モデルも予測も PostgreSQL に保存します。

## 必要なもの

| 項目 | 内容 |
|:---|:---|
| [Bun](https://bun.sh/) | 1.3 以上(実行環境) |
| [pnpm](https://pnpm.io/) | 依存パッケージの管理 |
| PostgreSQL | 18 で動作確認 |
| Chromium | Web UI だけで使用 |

## DB の準備

管理者(`postgres`)で次を実行します。パスワードは対話入力にして、シェル履歴へ残さないようにします。

```sql
CREATE ROLE skylark WITH LOGIN;
\password skylark
CREATE DATABASE skylark WITH OWNER = skylark ENCODING = 'UTF8';
```

TCP で接続する場合は、`pg_hba.conf` に `host skylark skylark 127.0.0.1/32 scram-sha-256` のような行が必要です。

テーブルは起動時に自動で作成されます(Drizzle のマイグレーション)。

## セットアップ

```bash
git clone git@github.com:m10i-0nyx/skylark.git
cd skylark
pnpm install
cp .env.example .env    # POSTGRES_PASSWORD などを編集する
```

Web UI を使う場合は、Chromium を用意します。

```bash
# Playwright が管理するブラウザを入れる
pnpm exec playwright install chromium-headless-shell

# または OS のブラウザを使う(.env の CHROMIUM_EXECUTABLE_PATH へ指定する)
sudo dnf install -y chromium-headless at-spi2-atk
```

## 使い方

```bash
# レース一覧の更新(-U) → ダウンロードと保存(-S) → 特徴量の計算(-F)
bun run src/cli.ts -U -S -F

# 指定したレースだけ取得する
bun run src/cli.ts -S 202501010101 202501010102

# 勝率モデルの学習(-T) → 当日開催の中央競馬の予測と抽出(-P) → 確定後の結果との突き合わせ(--report)
bun run src/cli.ts -T
bun run src/cli.ts -P
bun run src/cli.ts --report

# Web UI(既定は http://127.0.0.1:8501/)
# 画面のJSとCSSを dist/webui へ作ってから起動する
# 上の操作は、画面の「操作」(/operations)からもすべて実行できる
pnpm webui
```

`scraper.sh` と `webui.sh` は、それぞれ上の `cli.ts` と Web UI を起動するだけの短いスクリプトです。`webui.sh` も、起動前に画面のJSとCSSを作ります。

### コマンドラインオプション

| オプション | 内容 | 既定値 |
|:---|:---|:---|
| `-U`, `--update-race-list` | レース一覧を更新する(取得済みの日は通信せず `--temp` の `race_day.<YYYYMMDD>.txt` を使う。今日と昨日は毎回取得する) | - |
| `-S`, `--scraping` | レース結果をダウンロードして保存する | - |
| `-F`, `--feature` | 特徴量を計算する | - |
| `-Rf`, `--rebuild-feature` | 特徴量テーブルを空にして計算し直す | - |
| `-T`, `--train` | 勝率モデルを学習し、評価を表示して DB へ保存する | - |
| `-P`, `--predict` | 当日開催の中央競馬を予測し、条件に合う馬を抽出する(`race_id` で絞れる) | - |
| `--report` | 保存済みの予測を、確定した結果と突き合わせる | - |
| `--date DATE` | `--report` の開催日(`YYYY-MM-DD`) | 今日 |
| `--history-since DATE` | `-T` と `-P` が履歴に使う最初の開催日 | `2025-01-01` |
| `--min-odds N` | 抽出: 単勝オッズが N 倍以上 | `10` |
| `--min-popularity N` | 抽出: 人気が N 位以下(数字が大きいほど不人気) | `4` |
| `--max-rank N` | 抽出: モデルの勝率が N 位以内 | `5` |
| `--min-ev N` | 抽出: 期待値(モデルの勝率 × オッズ)が N 以上。0 で条件にしない | `1` |
| `--verbose` | `-P` で全レース・全出走馬を表示する | - |
| `--rebuild-all-tables` | 全テーブルの行を削除する | - |
| `--temp DIR` | HTML のキャッシュを置くディレクトリ | `./temp` |
| `--race-list-file FILE` | レース一覧のファイル名(`--temp` の下) | `race_list.txt` |
| `--period-of-months N` | 一覧を遡る月数 | `12` |
| `--debug` | デバッグログを出す | - |
| `race_id ...` | 取得するレース ID(`-S` と併用。省略時は一覧ファイル) | - |

終了コードは、正常が 0、処理の失敗が 1、引数の誤りが 2 です。

### 環境変数

`.env.example` を参照してください。DB の接続先は、`DATABASE_URL` または `POSTGRES_*` で指定します。
パスワードの既定値はありません。

### 勝率が高いのに人気がない馬の抽出

**仕組み**

1. 馬・騎手・調教師の過去成績から、レースごとの特徴量を作ります(16 項目)。**そのレースより前の開催日の結果だけ**を使い、同じ日のレースの結果は混ぜません。学習と当日の予測は同じコードで計算します。
2. 単勝オッズから、控除率を除いた**市場の勝率**を求めます(`(1/オッズ) / Σ(1/オッズ)`)。
3. 市場の勝率を土台に、過去成績で補正する**条件付きロジット**(レース内ソフトマックス)で、モデルの勝率を見積もります。市場を土台にするのは、過去成績だけで作った勝率は市場の持つ情報(調教・状態など)を知らず、市場より高く見える馬の多くが「見落とし」ではなく「情報不足」になるためです。
4. 次の条件をすべて満たす馬を抽出します。値は上のオプションで変えられます。
   - オッズが高い(既定: 10 倍以上)
   - 人気が低い(既定: 4 位以下)
   - 勝率が高い(既定: モデルの勝率がレース内の上位 5 位以内)
   - 期待値が見合う(既定: モデルの勝率 × オッズ ≥ 1)
5. 当日のレースは、出馬表のオッズを取得した時刻とともに `prediction_tbl` へ保存します。レースが終わって結果を取り込んだら、`--report` で予測と突き合わせられます。

**学習の手順(`-T`)**

1. 最後の約 100 日をテスト期間として取り分け、その前の約 10 か月を、61 日ずつ 5 つの区間に分けます(開発期間)。
2. 各区間を、**その区間より前の全期間で学習したモデル**で評価します(ウォークフォワード)。L2 正則化の強さは、候補(100・300・1000・3000)ごとに全区間の対数損失の平均を求めて選びます。1 つの検証期間だけで選ぶより、ぶれにくくなります。
3. 選んだ L2 で、開発期間だけを使って学習したモデルを、一度も使っていないテスト期間で評価します。
4. **保存するモデルは、テスト期間も含む全期間で学習し直したもの**です。最新のレースを捨てないためです。成績は、再学習する前の同じ手順のモデルで測っているので、保存したモデルそのものを測った値ではありません。
5. 対数損失の改善は、レースごとの差の平均を、**開催日ごとにまとめた標準誤差**とともに報告します。同じ日のレースは結果が相関するため、レース数だけで誤差を見積もると小さく見えすぎます。改善が標準誤差の 2 倍に届かない場合は「誤差の範囲です」と表示します。

**検証の結果(2026-10 時点、中央競馬)**

- 開発期間は 2025-09-03〜2026-07-04(2,838 レース、5 区間)、テスト期間は 2026-07-05〜10-12(972 レース)です。L2 は 1000 が選ばれました。
- 市場の勝率に対するモデルの上積みは**ごくわずか**です。対数損失の改善は、開発期間で 0.0043 ±0.0015(標準誤差の約 2.9 倍)、テスト期間で 0.0026 ±0.0030(誤差の範囲)です。**開発期間の値は L2 の選択に使った区間の値で、やや良く出ます**(L2 を 100 にすると 0.0033 ±0.0022 で、誤差の範囲です)。一度も使っていないテスト期間では誤差と区別できないため、**改善が確かだとはまだ言えません**。市場の対数損失(約 1.9)の 0.2% 程度で、区間ごとのぶれも大きい値です。
- 改善の中身を分けて調べると、市場の確率にかける係数(1.09)だけでは市場を上回れません(+0.0003 ±0.0003)。上積みは過去成績の特徴量によるものです。
- 抽出した馬は、開発期間で 41 頭(的中率 9.8%、回収率 149%±73%)、テスト期間で 12 頭(8.3%、83%±83%)です。**どちらも 100% との差は誤差の範囲内**です。L2 を 100 にすると、開発期間の抽出は 216 頭で回収率 88%±26% でした。L2 や期待値の条件を変えるたびに回収率の高低が入れ替わり、偶然のぶれと区別できません。
- 参考として、オッズ 10 倍以上かつ人気 4 位以下の馬を全頭買うと、回収率は 66〜74% です。
- L2 を大きくするとモデルが市場に近づくため、抽出される馬は減ります(テスト期間で L2=100 は 57 頭、L2=1000 は 12 頭)。
- 抽出条件は開発期間とテスト期間の両方を見て調べたため、成績は完全には独立していません。**今日以降の予測を保存して `--report` で突き合わせることが、本当の検証になります。**

**試して、採用しなかったこと**(開発期間で、あらかじめ決めた基準 = 標準誤差の 2 倍を超えて改善し、5 区間のうち 3 区間以上で改善、を満たしたものだけを採用する方針で評価しました)

- 特徴量の追加: 勝ち馬とのタイム差、脚質(通過順)、クラスの変化、距離・路面の変化、騎手の継続、馬番の位置の 6 グループ(計 12 項目)を 1 つずつ足しましたが、基準を満たすものはありませんでした。最良の「タイム差」でも −0.0002 ±0.0001 です。すべて足すと悪化します(+0.0008)。学習データが 3,000 レース程度では、特徴量を足しても過学習になります。
- 助走期間(`burnInDays`)を 90 日から 0〜60 日に短縮: 差はありません(z=−0.3〜+0.5)。
- 履歴の厚さ(履歴の開始日を 2025-01・04・07 と変える): 差はありません。
- 一方、**学習に使うデータの量は効きます**。評価区間を同じにして、直近 90 日だけで学習すると −0.0023、180 日で −0.0038、270 日で −0.0052、全期間(10〜15 か月)で −0.0066 と、一貫して改善します。保存するモデルを全期間で学習し直すのはこのためで、2017〜2024 年のレースを取り込んで学習データを増やすと、さらに安定する見込みがあります(ただし古い年のオッズ・馬の履歴が現在と同じ性質かは、取り込んで評価する必要があります)。

結論として、**このモデルは「市場が見落としている馬」を見つけたと言える段階にはありません**。市場に対する上積みは小さく、抽出された馬の回収率も誤差の範囲です。

**注意**

- 当日の予測は**中央競馬のみ**です。出馬表の一覧(`race.netkeiba.com/top/race_list.html`)が中央競馬だけを返すためです。地方競馬の履歴は、馬の過去成績として使います。
- 発売中のオッズは暫定値で、発走直前までに動きます。一方、モデルは確定オッズで補正を学んでいます。発走に近い時刻に実行するほど、学習時の条件に近づきます。
- 馬体重は発走前だと未発表(`999`)のことがあるため、特徴量に使っていません。
- DB の履歴は 2016 年分と 2025 年以降に分かれ、2017〜2024 年がありません。2016 年分は 2025 年以降の馬とほとんど重ならず、離れているため、既定では `--history-since 2025-01-01` で使いません。2017〜2024 年のレースを取り込めば、学習データが増えて推定が安定します。
- `-P` の前に `-U -S` で前日までの結果を取り込んでください。最新の結果が前日より古い場合は警告します。
- 予測とモデルは再取得できない記録(取得時のオッズ)のため、`--rebuild-all-tables` では削除しません。

### Web UI での操作

コマンドラインの操作は、Web UI の「操作」画面(`/operations`)からもすべて実行できます。選んだ処理は、コマンドラインと同じ順(テーブルの削除 → `-U` → `-S` → `-F` → `-T` → `-P` → `--report`)で実行します。始めた処理はジョブの画面(`/jobs/<ID>`)へ移り、ログと報告(コマンドラインの標準出力に当たる内容)を約 1 秒ごとに更新して表示します。ジョブの画面には、同じ内容をコマンドラインで実行する場合の引数も出ます。

| コマンドライン | 操作画面 |
|:---|:---|
| `-U` `-S` `-F` `-T` `-P` `--report` | 「実行する処理」のチェック欄 |
| `-Rf` `--rebuild-all-tables` | 「データを消す操作」のチェック欄(確認欄のチェックが必須) |
| `--period-of-months` `--race-list-file` `--date` `--history-since` `--min-odds` `--min-popularity` `--max-rank` `--min-ev` | 「設定」の入力欄(空欄は既定値) |
| `--verbose` `--debug` | 「設定」のチェック欄 |
| `race_id ...` | 「レース ID」(空白・改行・カンマ区切り) |
| `--temp` | 画面からは指定できません(サーバーで `./temp` に固定) |
| `-h`, `--help` | なし(画面の説明が代わりです) |

入力は、コマンドラインと同じ検証(`parseCliArguments`)を通します。そのうえで、画面からは次の制限を加えています。ネットワークから届く入力になるためです。

- 一覧を遡る月数は 1〜240、レース ID は 500 件までです。
- レース一覧のファイル名は、英数字と `.` `_` `-` だけです(フォルダは指定できません)。
- レース ID は数字だけです(`-` で始まる値がオプションとして解釈されることはありません)。
- `--rebuild-all-tables` と `-Rf` は、確認欄にチェックしないと実行されません(サーバーでも確かめます)。

動作の注意点です。

- 同時に実行できるジョブは 1 件です。実行中は新しいジョブを始められません。この制限が効くのはサーバーの中だけです。Web UI のジョブとコマンドライン(別のプロセス)を同時に動かすことは防げないため、テーブルを削除する操作(`-Rf` `--rebuild-all-tables`)は、他の処理が動いていないときに実行してください。
- **実行中のジョブを途中で止める機能はありません。** サーバーを停止する(`SIGINT` / `SIGTERM`)と、実行中のジョブの終了を待ちます。待たずに終わらせるには、もう一度シグナルを送ります。
- ジョブはサーバーのメモリにだけ保持します。最新 20 件、1 件あたりログ 2,000 行・報告 20 万文字までで、サーバーを再起動すると消えます。
- `-P` は、閲覧画面と同じ Chromium を使います。
- 報告は端末向けに桁を揃えて作られます(全角は半角 2 文字分)。ブラウザではフォントによって全角の幅が変わるため、画面では全角の文字を 2 文字分の幅に揃えて表示します(`src/webui/terminal-text.tsx`)。文字そのものは変わらないので、コピーした内容はコマンドラインの出力と同じです。
- ジョブのログは、サーバーの標準エラー出力にも出ます。

**公開範囲**: 認証がないため、既定(`WEBUI_HOST=127.0.0.1`)の自分の PC からのアクセスでだけ操作画面を使えます。`WEBUI_HOST` でそれ以外のアドレスを指定した場合、操作画面は無効です(`/operations` と `/jobs/...` は 404)。有効にするには `WEBUI_ENABLE_OPERATIONS=1` を設定します。その場合、到達できる誰もが全テーブルの削除や大量のダウンロードを実行できるため、ネットワーク側で制限してください。

### Web UI の画面

画面はサーバーで描画し(React の `renderToString`)、ブラウザ側のスクリプト(`src/webui/client.tsx`)が同じ値で引き継ぎます。選択欄などの操作はこの引き継ぎ後に動きます。

- `src/webui/views.tsx`: 画面の部品。サーバーとブラウザの両方で使います。
- `src/webui/components/ui/`: shadcn/ui の部品。設定は `components.json`、テーマは `src/webui/styles.css` です。
- ダーク/ライトは OS の設定(`prefers-color-scheme`)に従います。

部品を足すときは、次のコマンドを使います。

```bash
pnpm exec shadcn add <部品名>
```

追加後は `pnpm exec biome check --write src/webui` で整形してください。

テーブル定義を変えたら、次のコマンドでマイグレーションを生成します。起動時に未適用分が自動で適用されます。

```bash
bun run db:generate
bun run db:migrate
```

## Python 版(MySQL)からの移行

- `temp/` の `race.<id>.html.zst` は、そのまま使えます。キャッシュがあるレースは通信せずに `temp/` から読み込まれるため、DB の再構築に使えます。
  - レース ID を指定しない `-S` が対象にするのは `temp/race_list.txt` に載っているレースだけです。一覧に載っていないキャッシュ(例：古い年のもの)は、`bun run src/cli.ts -S <レースID>...` のように ID を指定してください。
  - 一覧に載っていてキャッシュが無いレースは、サイトから取得するため通信が発生します。
  - `-U` は、取得できた日ごとの一覧を `temp/race_day.<YYYYMMDD>.txt` に保存し、次回からその日は通信しません(初回は従来どおり時間がかかります)。取得し直したい日は、このファイルを削除してください。
- MySQL のデータを引き継ぐ機能はありません。上の方法で作り直してください。
- 環境変数は `MYSQL_*` から `POSTGRES_*` へ変わりました。
- 保存内容の違い
  - 完走タイムは 0.1 秒の精度で保存されます。MySQL の `TIME` は秒に丸めていました。
  - 特徴量は jsonb のオブジェクトとして保存されます。Python 版は JSON 文字列を JSON として二重に保存していました。
  - 特徴量の平均値は、Python 版が内部の型の都合で保存に失敗する場合がありました。今回は数値で保存します。
  - 騎手・調教師・馬主の ID は、先頭の 0 を保つ文字列です。

## 既知の制約

- 特徴量テーブル(`feature_tbl`)の `sppeed_figure_last`、`speed_figure_avg`、`winner_avg`、`disavesr` は、タイム指数が未ログインでは取得できず全件 `null` です(`winner_avg` は `speed_figure` が `null` でない出走だけを対象にするため)。勝率の予測には使わず、`src/predict/` が履歴から直接計算します。
- 結果表の列は、位置ではなく見出しの文字列で決めています。旧形式(21 列)と現行(25 列)のどちらも解析できます。必須の見出しが無い、または行の列数が見出しと違うページは、`ParseError` としてログへ記録し、そのレースの結果は保存しません。
- レース一覧(`-U`)は、月のカレンダー API(`/race/ajax_race_calendar.html`)から開催日を集めます。今月から `--period-of-months` か月ぶんを遡り、今日より後の日は取得しません。中央競馬と地方競馬の両方が対象です。
- ばんえい競馬(レース ID の 5〜6 桁目が `65`)は対象外です。馬 ID が `B202300104` のような英数字で、DB の馬 ID(数値)に保存できないため、一覧(`-U`)から除外します。レース ID を指定した `-S` では除外しないため、指定すると解析に失敗します。
- タイム指数などの指数系の列は、プレミアム会員向けで、未ログインでは `**` になります。`speed_figure` は未ログインのとき `null` です。
- 自動ログインの Cookie は、後続のダウンロードに引き継がれません(Python 版と同じ)。
